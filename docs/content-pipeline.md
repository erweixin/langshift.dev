# 内容生成管线：课程、练习与个性化重写

> 这篇讲一件事：每天的课程和练习不能每次都从零生成，也不能不检查就发给用户。我们要先生成一份多人可复用的“课程底稿”，跑过校验后缓存；用户需要的浅一点、换类比、按个人经验改写，再叠加在自己的版本上。执行链路见 [product-to-platform.md](./product-to-platform.md)，成本假设见 [unit-economics.md](./unit-economics.md)。

几个词先说清：

- **基座**：多人共享的课程底稿，先校验，再缓存。
- **delta**：用户自己的改写补丁，不改共享底稿。
- **level_band**：粗粒度能力档位，比如初级 / 中级 / 高级，不是完整个人画像。
- **cache key**：决定“这份内容能不能复用”的那串参数。

## 问题、决策与风险

**问题**：每个用户每天都要一篇课程：正文、类比、练习、测试、判断点。如果每个人都重新生成一整篇，DAU 一涨成本就跟着烧；而且模型偶尔会写出跑不通的测试或错误参考解，不能直接送到用户面前。

**决策**：内容分两层。第一层是跨用户共享的“基座”：同一任务、同一水平段的人共用，生成后必须通过机器校验才算定稿。第二层是每个用户自己的“改写层”：讲浅一点、换类比、按用户背景改写，只影响这个用户，不污染基座。所有内容都有版本，出问题能回滚。

**忽略后果**：要么成本失控，要么质量失控。最坏的情况是又贵又不稳定。

## 管线阶段

```text
TaskSpec ──▶ LessonPlan ──▶ Draft ──▶ 校验 ──▶ ContentArtifact（定稿，内容寻址）
（路线+画像段）  （结构化骨架）  （强模型）  （机器+抽样人审）        │
                                                        ▼
                                              个性化层（每用户 delta，小模型）
```

| 阶段 | 输入 | 输出 | 模型 |
| --- | --- | --- | --- |
| TaskSpec | 任务 + 路线阶段 + 水平段（不是个人画像） | 把“今天学什么”说清楚：判断点、前置概念、练习形态 | 无，规则组装 |
| LessonPlan | TaskSpec | 课程大纲：每节讲什么、练习长什么样、测试要考什么 | 中 |
| Draft | LessonPlan | 正文、类比、起始代码、测试、**参考解** | 强 |
| 校验 | Draft | 通过就定稿；失败就带原因重生成，最多 N 次 | 无 + 小模型辅助 |
| 定稿 | 通过的 Draft | ContentArtifact，写入缓存，供同类用户复用 | — |

## 校验：坏内容不出门

定稿前必须先过机器校验。这里不相信“模型说它验证过”，只相信真正跑出来的结果：

1. **参考解必须通过全部测试**——在 exercise runtime 里真实执行（见 [exercise-runtime.md](./exercise-runtime.md)）。
2. **测试必须能挂掉起始代码**——起始代码直接跑测试应当失败，否则练习没有区分度。
3. **判断点覆盖**：至少一条测试标记为判断点，且与 TaskSpec 的判断点文本对应。
4. **结构 lint**：节数、字数区间、练习位置、目录锚点、禁用词。
5. **安全检查**：练习代码不含网络 / 文件系统调用，和运行时白名单形成双保险。

校验失败带着失败原因重新生成（原因进 prompt）；连续 N 次失败进入人审队列而不是硬着头皮下发。

## 缓存与复用

```text
cache_key = hash(task_template_id, target_stack, level_band, content_version, prompt_version)
```

- **level_band 不是个人画像**：这里只按能力大档分，比如初级 / 中级 / 高级。同档用户共享同一份基座。个人偏好放在 delta 层，不放进 cache key，否则每个人都变成独一份，缓存就失效了。
- 命中即跳过整条生成管线（成本 ≈ 0）；未命中生成后写回，第二个同档用户开始免费。
- 命中率是单位经济的核心变量（见 [unit-economics.md](./unit-economics.md)）：路径越标准化（js2py、前端→Agent 这类既定路线），命中率越高；完全自定义目标的用户命中率低，是成本上的重用户。
- `content_version` / `prompt_version` 变更使旧缓存自然失效，可灰度、可回滚。

## 个性化层：delta 不污染基座

用户对内容的每次干预都作用在**自己的 delta** 上：

| 干预 | 机制 | 沉淀 |
| --- | --- | --- |
| 选中「讲浅一点」/「换个类比」 | 小模型带选中段落 + 前后文 + 偏好实时重写，替换渲染层的该段 | delta 记录（段落锚点 → 重写文本）+ 偏好写入画像 |
| 偏好已知（画像里有讲解偏好） | 渲染课程时对基座做**预重写**：只重写受偏好影响的段落 | 同上，用户无感知 |
| 「太难了」降级 | 不改内容，换 TaskSpec 重新走管线（多数会命中更低 band 的缓存） | 难度信号进画像 |

规则：**基座只读、delta 每用户、重新打开课程时必须把 delta 再叠上去**。用户点过“讲浅一点”后，系统承诺“之后也按这个深度讲”，靠的就是这套机制。

## 质量反馈回路

| 信号 | 采集点 | 用途 |
| --- | --- | --- |
| 练习通过率 / 平均尝试次数 | exercise runtime | 过低 → 内容过难或测试有坑 |
| 「太难了」点击率 | UI | band 划分校准 |
| 选中重写率（按小节） | UI | 哪些小节写得不好，定位到段落 |
| Review 失败模式 | ReviewCompleted | 判断点没教到位 |
| golden set 回归 | 每条路线固定 N 个任务的人工基准 | prompt_version 升级前的门槛测试 |

新 prompt_version 上线流程：golden set 全绿 → 灰度 10% 新生成 → 观察上表信号 → 全量。

## Lite v0 实现建议

- 缓存表就是 PostgreSQL/SQLite 一张 `content_cache`（key → artifact JSON），先不需要对象存储。
- 人审队列先等于一个状态字段 + 创始人自己看，不做后台系统。
- v0 只有一条主路线（前端 → Cloud Agent），level_band 先只分 1 档。流程照样走，缓存自然高命中；等有第二条路线再细分。

## Do / Don't

| 应该 | 不应该 |
| --- | --- |
| 参考解跑真测试后才定稿 | 相信模型自称"测试已验证" |
| 个性化做成 delta 层 | 把个人画像放进基座 cache key |
| 失败原因回灌重生成 prompt | 无限重试同一个 prompt |
| golden set 挡 prompt 升级 | 直接全量换 prompt |
| 记录每次生成的 token/cost | 只记"生成成功" |
