# Lites Enterprise private delivery

This runbook defines the supported customer-controlled Kubernetes delivery. It is a production topology, not the hermetic `foundation.compose.yaml` development stack. Every release is installed from one immutable bundle and one image lock; mutable tags and mixed release versions are unsupported.

## Delivery boundary

The customer owns the cloud account, Kubernetes control plane, PostgreSQL, object storage, KMS/HSM, secret manager, DNS, certificates, SMTP and observability destination. Lites supplies signed multi-architecture images, Helm and OpenTofu sources, database migrations, contract schemas, SBOMs, provenance, vulnerability results and the commercial license entitlement. No plaintext customer secret or vendor support account is included.

macOS is supported for control-plane development. Firecracker installation, kernel/rootfs preparation, KVM checks and local Firecracker validation are skipped on macOS. A delivered environment that enables sandbox execution must provide separately hardened Linux KVM runtime hosts; this requirement does not apply to the macOS development workstation.

## Immutable bundle verification

1. Verify the detached signature on `bundle-manifest.json` using the offline release public key pinned in the contract.
2. Recompute every artifact SHA-256 listed by the bundle manifest before importing anything.
3. Verify each OCI image by digest, its Cosign signature and SLSA provenance. Confirm the provenance source revision and build workflow match the bundle manifest.
4. Import the image set into the customer registry without changing manifests. Generate `image-lock.json` using the destination repository and the same platform manifest digest.
5. Reject the bundle if an image lacks its CycloneDX SBOM or has an unresolved HIGH/CRITICAL vulnerability result. Do not accept mutable tags as evidence.

The current engineering artifact is built only after `npm run verify:macos` with `npm run release:engineering-rc`; it is explicitly not a Commercial GA artifact. After every Commercial GA prerequisite has separately produced real, signed production evidence, the legacy delivery verifier is invoked through the deliberately named preflight commands: `npm run commercial:ga-preflight:candidate`, `npm run commercial:ga-preflight:install`, and `npm run commercial:ga-preflight:readiness`. The installer rejects caller-selected publisher identities, dirty or mismatched commits, missing Sigstore bundles, incomplete image catalogs, and altered source artifacts. A merely present bundle, a fixture report, or a signature from another identity remains pending and cannot change the Engineering RC status into Commercial GA.

Every final Stage 1–6 gate, profile evaluation, capacity, recovery and deployment report also carries a detached Sigstore bundle and a deterministic `reportHash`. Exact authorized identities are committed in `stage6EvidenceAuthorities`; runtime environment variables cannot replace them. The penetration-test provider, pilot-report authority and final release authority start with empty allowlists and therefore fail closed until accountable parties are contractually selected and their exact certificate identities are reviewed in a source change. Adding an authority invalidates the prior RC and requires a new signed candidate. Post-RC evidence is installed under the ignored `release-evidence/current` layout defined by `contracts/release/stage6-evidence-layout.json`; it is never written back into tracked source as part of the RC. This removes the otherwise impossible cycle between clean-source attestation and evidence generated after the RC exists.

Deployment drill automation emits one JSON Lines record per real operation attempt. Generate a report only from a clean checkout of the exact RC with `node scripts/write-stage6-deployment-report.mjs --target <compose|helm-tofu|official-cloud> --source-commit <commit> --rc-hash <hash> --evidence-jsonl <records.jsonl>`. The writer requires exactly three consecutive passes for fresh installation, upgrade, backup, restore and application rollback. Every attempt binds the environment, transcript and before/after state hashes; verifies schema 84, logical-data reconciliation, deletion replay, health and security checks; and requires a new Store Epoch for restore while forbidding an epoch change for non-restore operations. The generated summary and copied raw JSON Lines evidence must then be signed by the authorized automation identity. Handwritten summary JSON is not accepted by readiness.

The official capacity runner records contiguous one-minute JSON Lines windows from the immutable RC. Convert them with `node scripts/write-stage6-capacity-report.mjs --source-commit <commit> --rc-hash <hash> --evidence-jsonl <samples.jsonl>`. The writer rejects fewer than 30 steady-state minutes, fewer than five minutes at 2× load, more than 15 minutes of recovery, discontinuous windows, configuration or image-lock drift, any SLO breach from `docs/operations.md`, any tenant-isolation success, or a backlog that is not normalized for the last three windows. The signed summary remains bound to the copied raw samples by SHA-256.

Recovery automation records three consecutive attempts for instance/AZ failure, full-region recovery and queue loss. Convert the nine records with `node scripts/write-stage6-recovery-report.mjs --source-commit <commit> --rc-hash <hash> --evidence-jsonl <records.jsonl>`. RPO and RTO are calculated from acknowledged/recovered-write and fault/resumed-traffic timestamps. The writer rejects instance/AZ data loss or recovery beyond five minutes, regional RPO above five minutes or RTO above one hour, queue recovery above 15 minutes, regional Store Epoch reuse, acceptance of an old-epoch command, missing EventStore facts or object references, duplicate effects, incomplete command recreation, accounting mismatch, or failure to replay account-erasure tombstones.

Each Agent Profile is evaluated against its exact 200-sample bilingual specialist slice and all 600 shared bilingual end-to-end samples. Record both the approved baseline and RC candidate output for every sample, including provider attempt, immutable behavior/model/prompt/tool/policy/context hashes, cost, latency, deterministic checks and two distinct reviewers' complete rubric scores. Generate each signed report with `node scripts/write-stage6-profile-eval-report.mjs --profile <profile> --source-commit <commit> --rc-hash <hash> --evidence-jsonl <records.jsonl>`. Exactly 1,600 execution records are required per Profile. The writer calculates dimension means and acceptance rates, language and transition-group rates, reviewer agreement, worst baseline regression, cost and p95 latency; any safety redline fails the whole Profile regardless of averages.

Pilot and final release approval use five source-bound Ed25519 public keys in `contracts/release/stage6-approver-keyring.json`; private keys are never stored in the repository or delivery bundle. The keyring remains `unassigned` and verification fails closed until the accountable product/research or engineering/security/privacy or operations/QA/release principals are selected. Each signature binds its approval type, role, approver and key identities, exact RC hash, complete evidence-manifest hash, immutable approval-scope hash, decision and time. Use `npm run release:stage6-approval-sign -- --report <path> --type <pilot|final> --role <role> --approver-id <id> --key-id <id> --private-key <external.pem>`; duplicate identities, revoked keys, altered evidence, and signatures copied from another RC are rejected.

GitHub issues are not release evidence. The official RC workflow, readiness verifier and installer do not query, package, sign or inspect issue counts, contents or labels; project-management issue tooling cannot pass or fail an Engineering RC or Commercial GA engineering check.

Pilot equivalence is computed, never asserted manually. Preserve the approved pilot behavior manifest as `pilot-reports/product-behavior-manifest.json`, then run `npm run release:stage6:pilot-equivalence -- --pilot-manifest pilot-reports/product-behavior-manifest.json --rc-manifest release-candidates/current/product-behavior-manifest.json --pilot-report release-evidence/current/pilot-approved.json --release-candidate release-candidates/current/ga-release-candidate.json --output release-evidence/current/pilot-rc-behavior-equivalence.json`. The writer compares every pilot-scoped component hash, its exact input set, and the impact rules; any addition, removal or change produces a failed report. The raw pilot report, pilot manifest, RC manifest and RC hashes are embedded in the summary and rechecked by readiness before its detached signature is trusted.

The pilot report itself is generated from the frozen protocol, consent document, cohort manifest, pilot behavior manifest, metric summary and one closed-contract deidentified JSON Lines outcome per consented participant. Run `npm run release:stage6:pilot-report -- --cohort pilot-reports/cohort-manifest.json --behavior-manifest pilot-reports/product-behavior-manifest.json --metrics pilot-reports/evidence/pilot-metrics.json --event-dataset pilot-reports/evidence/pilot-events.jsonl --output release-evidence/current/pilot-approved.json` from the clean RC source. The writer recomputes all five denominators and numerators overall, by locale and by transition stratum; requires 60 consented participants, 30 per locale, six strata with five participants per locale, 28 days, complete withdrawal deletion receipts, no prohibited content fields, no protocol deviations, no group more than 15 points below the overall metric, and six zero-tolerance counts at zero. It binds every raw input hash, image lock, configuration, analysis code and RC into `evidenceManifestHash`; the report cannot satisfy readiness until five distinct pilot roles sign that exact approval scope and the detached source-authorized Sigstore bundle also verifies.

The selected independent penetration-test provider records the complete engagement in `release-evidence/current/evidence/external-penetration-test.json` and generates the summary with `npm run release:stage6:penetration-report -- --evidence-json release-evidence/current/evidence/external-penetration-test.json --output release-evidence/current/external-penetration-test.json` from a clean checkout of the RC. The writer requires two or more testers, provider contract and independence-attestation hashes, the exact image lock and environment, and all fourteen application, control-plane, tenant, identity, AI, egress, sandbox, secret, approval, recovery and deletion scopes. Critical or High findings must be closed with retest hashes. Cross-tenant access, secret exposure, unauthorized side effects, data corruption and approval bypass may never be accepted as risk at any severity and must be resolved. Readiness also verifies the raw engagement hash, report freshness and the detached signature against the source-approved external authority.

After every prerequisite report and its detached signature has been installed in the exact evidence layout, run `npm run release:stage6:final-approval`. The writer enumerates the source-locked layout instead of accepting caller-selected files, hashes all 64 required RC, raw, report, signature, pilot and legal artifacts, revalidates 18 prerequisite report hashes/statuses/source or RC bindings, and refuses inactive legal governance. The resulting `release-evidence/current/final-approval.json` begins with an empty signature set; five distinct final roles sign it with `release:stage6-approval-sign`. Any later byte change to any required artifact invalidates `evidenceManifestHash`, all five Ed25519 approvals, the detached final-authority Sigstore bundle and GA readiness.

## Prerequisites

- Kubernetes `>=1.33 <1.36` distributed across three failure zones.
- PostgreSQL 16 with PITR, synchronous in-region HA and per-service least-privilege roles.
- Customer KMS, versioned object storage, NATS JetStream, Valkey, External Secrets and an OTLP-compatible observability stack.
- A private registry reachable by every cluster node and a customer-operated certificate authority for workload mTLS.
- Dedicated DNS names for the public application and the restricted operations entry point.
- On Linux runtime hosts only: KVM, cgroup v2, approved Firecracker/kernel/rootfs catalog and isolated runtime subnets. These checks are intentionally not run on macOS.
- For account erasure: versioning and per-version deletion on both payload and artifact buckets, a dedicated `lites_erasure_worker` database role, per-subject Vault Transit key deletion, and subject-tagged Valkey cache keys. The exact privilege and restore procedure is in `runbooks/account-erasure.md`.

## Fresh installation

1. Create and lock the remote OpenTofu state backend. Apply the customer-reviewed module plan; never place PKI private keys or application peppers in state.
2. Create database roles (including `lites_erasure_worker`) before migrations, initialize the Store Epoch authority outside the EventStore failure domain, and write versioned workload bundles to the customer secret manager.
3. Run `lites-migrate` by digest as a one-shot identity. It must verify `deploy/migrations/manifest.json`, acquire the migration lock, apply forward migrations and run the matching `900xxx_verify_current.sql` verifier.
4. Render the Helm chart with every workload image set to a digest from `image-lock.json`, every `externalSecretRemoteKey` populated and every public origin/egress destination explicitly allowlisted.
5. Validate the render with JSON schema, kubeconform and Trivy before apply. Apply the chart and wait for all readiness probes, PodDisruptionBudgets and Store Epoch monitors to become healthy.
6. Run the signed smoke suite through the public ingress and restricted administrator ingress. Confirm tenant isolation, event append/outbox, reserve/settle/release, audit export, two-person contract approval and the account-erasure dependency preflight from `runbooks/account-erasure.md`.
7. Record cluster, database, image-lock, migration and behavior-manifest hashes in the installation evidence. Three consecutive fresh installations are required for a GA release candidate.

## Upgrade

1. Back up PostgreSQL and the Store Epoch anchor, then verify a restore in the recovery cell before changing production.
2. Verify the new bundle and compute the behavior-manifest delta. Any pilot-scoped change requires the Stage 4 equivalence or pilot rule.
3. Run expand-compatible migrations, deploy backward-compatible workers and services, then switch traffic. Destructive contract changes are forbidden in the same release.
4. Hold the previous image lock and chart values until SLOs, event lag, queue backlog, accounting reconciliation and privacy gates pass.
5. Run the post-upgrade verifier and preserve evidence. Three consecutive upgrades from the immediately previous supported release are required.

## Backup and restore

Back up PostgreSQL with continuous WAL, object versions, NATS streams, customer secret metadata, the Store Epoch anchor, Helm values, image lock and behavior manifest. Never copy plaintext application secrets into the bundle. A restore starts with a new recovery epoch, restores PostgreSQL and objects to the approved point, replays deletion tombstones, recreates streams from the database outbox where required, and only then admits commands. Validate `RPO/RTO`, accounting reconciliation and deletion receipts. Three consecutive backup and restore drills are required.

## Rollback

Application rollback uses the prior signed image lock and Helm revision only while the database remains expand-compatible. Never run a down migration against live customer data. If a release crossed an irreversible data boundary, execute forward recovery or restore into an isolated recovery cell, increment Store Epoch, validate, then cut traffic. Three consecutive rollback drills are required.

## Support handoff

The handoff contains architecture and data-flow diagrams, the exact image lock, SBOM/provenance set, configuration inventory, SLO/SLA schedule, escalation contacts, backup/restore evidence and expiry dates for the commercial license and support tier. Support access is customer-initiated, time-bounded, audited and uses customer identity; no permanent vendor credential is permitted.
