# Personal Growth OS UI/UE 蓝图

> 本文档沉淀 Lites 在产品交互层的设计方向：它不应该是普通课程平台、打卡工具或 AI Chatbot，而应该是一个状态驱动的成长工作流系统。产品总纲见 [product-growth-os.md](./product-growth-os.md)。

## 核心判断

Lites 的用户体验核心不是“展示一个完整成长系统”，而是持续回答用户每天打开产品时最关心的问题：

```text
我现在该做什么？
为什么是这一步？
我做完以后是否真的变强了？
这个产出能不能变成未来机会里的证据？
```

因此，首屏不应该从空白聊天框、复杂知识图谱或完整 Dashboard 开始，而应该根据用户状态展示一个明确主动作。

```text
新人：降低输入成本，尽快看到第一条迁移路径
进行中：减少决策，让用户推进今天一步
卡住时：降低难度，把任务拆小
断更后：温和重启，而不是羞辱式提醒
提交后：Review Evidence，并生成下一步
阶段结束：复盘能力变化，重排计划
```

一句话：

```text
少展示系统结构，多展示下一步行动。
```

## 和 Codex 的关系

可以借鉴 Codex 的状态透明和推进感，但不能照搬“任务线程 + workspace 变更”的界面重心。

Codex 的核心对象是：

```text
代码任务 -> Agent 执行 -> 文件变更 -> 测试验证 -> 用户确认
```

Lites 的核心对象应该是：

```text
成长目标 -> 今日行动 -> Lite Challenge -> Evidence -> Review -> 能力画像更新
```

值得借鉴的是：

- Agent 在做什么要可见。
- 需要用户介入时暂停并给出清晰选择。
- 产出要可追踪、可复盘。
- 用户可以随时继续、修正、取消或调整方向。

不应该照搬的是：

- 以聊天线程作为唯一主入口。
- 把系统过程展示得比用户行动更重要。
- 默认用户知道该问什么、该点什么、该如何推进。

## 产品主循环

MVP 的核心闭环应该先做窄：

```text
新人生成目标
→ Today 给出一个主任务
→ 用户执行或调整难度
→ 提交 Evidence
→ Coach Review
→ 生成下一步
→ 更新能力画像
```

更完整的长期循环：

```text
学一个概念
→ 用户用自己的话解释
→ 做 Lite Challenge
→ Agent Review
→ 修正一个关键误区
→ 进入真实项目任务
→ Evidence 作品化
→ 阶段复盘
```

## 信息架构

建议整体采用三栏结构，但中间状态区永远是主角。

```text
┌──────────────────────────────────────────────────────────────┐
│ Lites                 当前目标 / Today / Evidence / Map / Coach │
├───────────────┬────────────────────────────────┬─────────────┤
│ 目标与历史      │ 主状态区                         │ Coach / Context │
│               │ 根据用户状态变化                  │             │
│ 当前目标       │                                │ 能力画像       │
│ 历史目标       │                                │ 风险点         │
│ Evidence      │                                │ Agent Activity │
└───────────────┴────────────────────────────────┴─────────────┘
```

左侧回答“我在哪个目标里”，中间回答“现在该做什么”，右侧回答“为什么这样安排、Agent 正在做什么、我有哪些上下文”。

### 导航命名

`Mission` 是内部产品模型，但面向用户可以弱化这个词。用户更自然理解的是：

```text
当前目标
本周推进
今日一步
成长证据
能力地图
Coach
```

## 状态驱动草图

### 状态 1：新人首次进入

不要一开始要求完整建档。第一次体验的目标是让用户快速感到“它理解我的处境”。

```text
┌──────────────────────────────────────────────┐
│ 你现在想完成哪种变化？                         │
│                                              │
│ [转向 AI 产品经理] [前端 → 全栈] [学习复杂技能] │
│ [做一个作品集项目] [我还不确定]                 │
│                                              │
│ 你可以先给我一个材料：                         │
│ [上传简历] [粘贴 GitHub] [粘贴目标 JD] [跳过]   │
│                                              │
│ [生成第一条迁移路径]                            │
└──────────────────────────────────────────────┘
```

更短的冷启动也可以只问两件事：

```text
你现在是谁？
你想变成谁？
```

### 状态 2：AI 正在生成画像和目标

不要只展示 loading，要展示诊断过程。

```text
┌──────────────────────────────────────────────┐
│ 正在为你生成第一个成长目标                      │
├──────────────────────────────────────────────┤
│ ✓ 已读取你的背景信息                            │
│ ✓ 已识别可迁移能力：React、API、产品理解          │
│ … 正在判断目标能力缺口                           │
│ … 正在生成今天的第一步                            │
│                                              │
│ 你稍后会得到：                                  │
│ 当前优势 / 关键缺口 / 第一座迁移桥 / 今日行动      │
└──────────────────────────────────────────────┘
```

### 状态 3：首次目标生成完成

不要直接给完整 4 到 12 周大计划，先给“我理解你”和“今天第一步”。

```text
┌──────────────────────────────────────────────┐
│ 我建议你先试跑这个 7 天目标                      │
│                                              │
│ 前端工程师 → AI 应用工程师                       │
│                                              │
│ 我看到你的优势：                                │
│ React / API / 前端工程化 / 用户体验理解           │
│                                              │
│ 当前最关键缺口：                                │
│ LLM 应用评估、RAG 调试、模型边界判断              │
│                                              │
│ 今天第一步：                                    │
│ 记录 3 个模型失败回答，并解释失败原因              │
│                                              │
│ [开始今天任务] [调整目标] [先看看完整计划]          │
└──────────────────────────────────────────────┘
```

### 状态 4：日常使用中

Today 首页应该极简，只突出一个主动作。

```text
┌──────────────────────────────────────────────┐
│ 今天最重要的一步                                │
├──────────────────────────────────────────────┤
│ 记录 3 个模型失败回答，并解释失败原因              │
│                                              │
│ 预计 25 分钟                                   │
│ 为什么做：这是你从“会调用模型”进入“会评估 AI 应用” │
│ 的关键一步。                                    │
│                                              │
│ [开始] [太难了] [今天没时间] [换一个任务]          │
├──────────────────────────────────────────────┤
│ 本周节奏                                       │
│ Mon ✓  Tue ✓  Wed 今日  Thu ○  Fri ○            │
└──────────────────────────────────────────────┘
```

`太难了`、`今天没时间`、`换一个任务` 是关键按钮。真实用户不是每天都高度自律，产品需要承认这个事实。

### 状态 5：任务进行中

任务页不是普通待办，而是轻量工作台。

```text
┌──────────────────────────────────────────────┐
│ 任务：最小 RAG 失败分析                         │
├──────────────────────────────────────────────┤
│ Step 1  准备 5 个测试问题              ✓        │
│ Step 2  收集模型回答                  进行中     │
│ Step 3  标注 3 个失败 case             ○        │
│ Step 4  写 300 字复盘                  ○        │
│                                              │
│ Coach                                         │
│ “不要先优化架构。今天只验证你能否判断失败来自哪里。” │
│                                              │
│ [我卡住了] [检查我的理解] [提交产出]              │
└──────────────────────────────────────────────┘
```

### 状态 6：用户卡住或难度不匹配

不要把卡住视为失败，要把它视为计划需要调整。

```text
┌──────────────────────────────────────────────┐
│ 看起来这个任务有点重                             │
├──────────────────────────────────────────────┤
│ 你可以换成更小的一步：                            │
│                                              │
│ A. 只画出 RAG 流程图，今天不写代码                 │
│ B. 只收集失败回答，明天再分类                       │
│ C. 让我用你的技术栈重新拆一版                       │
│                                              │
│ [选 A] [选 B] [重新拆分] [和 Coach 说说卡点]       │
└──────────────────────────────────────────────┘
```

### 状态 7：用户断更后回来

断更后的体验要温和，目标是帮助用户重启，而不是追赶原计划。

```text
┌──────────────────────────────────────────────┐
│ 欢迎回来。我们把计划重新变轻一点。                 │
├──────────────────────────────────────────────┤
│ 你已经 6 天没有推进这个目标。                      │
│ 没关系，我建议先不要追赶原计划。                    │
│                                              │
│ 今天只做一个 20 分钟重启任务：                     │
│ 重新解释：RAG 里 retrieval 为什么影响回答质量       │
│                                              │
│ [20 分钟重启] [压缩本周计划] [重新规划目标] [暂停]   │
└──────────────────────────────────────────────┘
```

### 状态 8：提交 Evidence

Evidence 不是附件，而是成长证据。提交时要让用户表达不确定点，让 Review 更有针对性。

```text
┌──────────────────────────────────────────────┐
│ 提交今天的 Evidence                            │
├──────────────────────────────────────────────┤
│ 你完成了什么？                                  │
│ [Demo 链接 / GitHub commit / 文档 / 截图]         │
│                                              │
│ 你觉得哪里最不确定？                              │
│ [检索质量] [代码结构] [概念理解] [表达不清]          │
│                                              │
│ 希望 Coach 怎么 Review？                         │
│ [严格一点] [只看关键问题] [帮我改成作品集表达]       │
│                                              │
│ [提交 Review]                                  │
└──────────────────────────────────────────────┘
```

### 状态 9：Review 完成

反馈不要像考试批改，要像推进下一步。一次只抓一个最值得改的点。

```text
┌──────────────────────────────────────────────┐
│ Review 完成                                    │
├──────────────────────────────────────────────┤
│ 你已经做到：                                    │
│ ✓ 能把 RAG 拆成 query → retrieval → answer      │
│ ✓ 能观察到模型回答并不稳定                         │
│                                              │
│ 当前最值得改的一个点：                            │
│ 你把“回答不好”全部归因给 prompt，                  │
│ 但还没有检查 retrieval 是否拿到了正确上下文。        │
│                                              │
│ 下一步：                                        │
│ 补 3 个失败 case，并标注每个失败来自 retrieval、    │
│ generation 还是 data 问题。                     │
│                                              │
│ Evidence 状态：草稿 → 已 Review                  │
│                                              │
│ [生成明天任务] [改成作品集描述] [继续追问]          │
└──────────────────────────────────────────────┘
```

### 状态 10：阶段复盘

阶段复盘要让用户感到能力确实发生了变化。

```text
┌──────────────────────────────────────────────┐
│ Week 3 复盘                                    │
├──────────────────────────────────────────────┤
│ 本周你完成了：                                  │
│ ✓ 最小 RAG 失败分析                              │
│ ✓ 2 次技术复盘                                  │
│ ✓ 1 个可展示 Evidence                           │
│                                              │
│ 能力画像更新：                                  │
│ RAG 基础：○ → ◐                                │
│ AI 应用评估：○ → ◐                              │
│ 技术表达：◐ → ●                                │
│                                              │
│ 下周建议：                                      │
│ 从“能观察失败”进入“能设计 eval case”。             │
│                                              │
│ [接受下周计划] [调整节奏] [修改目标]               │
└──────────────────────────────────────────────┘
```

### 状态 11：Evidence 作品化

这是平台区别于普通学习产品的关键体验：学习产出要变成未来机会里的表达资产。

```text
┌──────────────────────────────────────────────┐
│ 这个 Evidence 已经可以作品化                      │
├──────────────────────────────────────────────┤
│ 原始产出：RAG 失败分析 + 复盘                      │
│                                              │
│ 可以生成：                                      │
│ [作品集页面] [简历 bullet] [面试讲述稿] [技术文章]  │
│                                              │
│ 推荐表达：                                      │
│ “我构建了一个最小 RAG 分析流程，并通过失败 case     │
│ 区分检索质量、生成稳定性和数据质量问题。”             │
│                                              │
│ [生成作品集版本] [继续打磨]                        │
└──────────────────────────────────────────────┘
```

## 如何判定用户学会了

不要用完成率判断用户是否学会。真正的判断标准是：

```text
用户能不能在更小、更真实、更迁移的场景里独立做出判断和产出？
```

每个能力节点可以分成五个状态：

```text
未接触
→ 看过
→ 能解释
→ 能做出 lite 版本
→ 能迁移到真实场景
```

以 RAG 为例：

```text
看过：读过 RAG 基础资料
能解释：能说清 query、chunk、retrieval、generation 的关系
能做 lite 版本：能用 5 段文本做一个最小检索回答流程
能迁移：能判断回答差是 prompt 问题、检索问题，还是数据质量问题
```

产品上不应该问“你听懂了吗”，而应该温和地追问：

```text
那你能不能做一个很小的版本？
能不能解释为什么这样做？
换一个场景你还会不会？
```

## Lite Challenge

每个关键能力节点都应该有一个低风险、低成本、可 Review 的 Lite Challenge。它不是考试，而是验证用户是否能把概念落到判断和产出。

示例：

| 能力 | Lite Challenge | 判断点 |
| --- | --- | --- |
| 理解 RAG | 不用向量库，只用 5 段文本 + 关键词匹配，做最小检索回答流程 | 能否区分 retrieval、generation、data 问题 |
| 理解 Agent | 设计一个只有 3 个工具的 Agent 流程图，并说明每一步失败怎么办 | 能否识别工具边界、失败路径和人工介入点 |
| 理解产品评估 | 为一个 AI 写作功能设计 5 个 eval case | 能否覆盖正常、边界、失败和主观质量场景 |
| 理解系统设计 | 画出单用户版架构，再说明扩展到多用户会坏在哪里 | 能否从功能实现进入约束和风险思维 |
| 理解 ProseMirror | 根据 document JSON 反推用户编辑动作 | 能否理解 document、selection、transaction 的边界 |

Lite Challenge 的 UI 可以作为 Today 的一种任务类型：

```text
┌──────────────────────────────────────────────┐
│ 验证你是否真的理解 RAG                         │
├──────────────────────────────────────────────┤
│ Lite Challenge                                │
│ 用 5 段文本设计一个最小 RAG 流程，并解释：        │
│ 如果回答错了，你会检查哪 3 个地方？              │
│                                              │
│ [开始 15 分钟挑战] [先看示例] [我还没准备好]      │
└──────────────────────────────────────────────┘
```

提交后，如果通过 Review，能力状态可以从 `能解释` 进入 `能做 lite 版本`。如果没有通过，不要打回大任务，而是生成一个更小的修正任务。

## Review 反馈结构

每次用户提交 Lite Challenge 或 Evidence 后，Coach 的反馈必须固定成可推进的结构：

```text
你已经做到什么
你误解了什么
你还缺哪一个关键判断
下一步只改一个点
是否升级到真实任务
```

示例：

```text
你已经做到：
✓ 能把 RAG 拆成 query → retrieval → answer

当前问题：
你把“回答不好”全部归因给 prompt，但没有检查 retrieval 是否拿到了正确上下文。

下一步：
请补 3 个失败 case，并标注每个失败是 retrieval、generation 还是 data 问题。
```

反馈的目标不是证明用户错了，而是把下一步变得更清楚。

## 对话处理

Coach 不能只是右侧聊天框。它应该根据用户对话意图，把自由对话转成可推进的学习状态。

常见对话类型：

```text
提问：我不懂这个概念
卡住：我做不下去了
解释：我试着讲一下我的理解
提交：这是我做的方案
反思：我发现我之前理解错了
改计划：今天没时间，能不能换个任务
```

对应处理：

| 用户意图 | Coach 响应 | 后续动作 |
| --- | --- | --- |
| 提问概念 | 先解释，再给例子 | 给一个 micro-check |
| 表达卡住 | 诊断卡点，不责备 | 拆小、换任务或给示例 |
| 复述理解 | 判断理解质量 | 引导到 Lite Challenge |
| 提交方案 | 进入 Review | 生成下一步或作品化 |
| 反思误区 | 记录能力画像变化 | 更新 Map 和复习点 |
| 改计划 | 调整节奏 | 生成更轻的 Today |

示例：

```text
用户：RAG 和普通搜索有什么区别？

Coach：
先解释差异，再追问一个 micro-check：
“如果模型回答错了，你会先检查 prompt 还是 retrieval？为什么？”
```

```text
用户：我的理解是 RAG 就是先搜索资料再让模型总结。

Coach：
这是一个可用的起点，但还不完整。
你漏了两个关键点：chunk 质量和检索召回。
要不要做一个 10 分钟 Lite Challenge？
```

关键原则：

```text
对话不能只是答疑，要自然引导到验证、行动或 Evidence。
```

## Coach 的产品定位

Coach 的核心不是“可以聊天”，而是在每个状态下减少用户的心理摩擦。

在不同状态下，Coach 应提供上下文动作：

```text
日常任务：[我卡住了] [帮我拆小] [检查我的理解]
提交后：[严格 Review] [生成作品集表达] [转成明天任务]
断更后：[20 分钟重启] [压缩计划] [暂停目标]
阶段复盘：[接受下周计划] [调整节奏] [修改目标]
```

Coach 需要用对话承接开放问题，但 UI 上不要只给空白输入框。默认给 2 到 3 个情境按钮，降低用户发起成本。

## Map 的 MVP 形态

完整 Knowledge Map 很容易变成“看起来很厉害，但用户不知道怎么用”的大图。MVP 里建议先做迁移卡片。

```text
你已经会：React state
可以迁移到：Agent state
关键差异：React state 可控，Agent state 受模型不确定性影响
今天任务：观察一次模型输出失败
```

等用户积累了足够多的迁移卡片、Lite Challenge 和 Evidence，再展开成完整 Map。

## Evidence 状态

Evidence 不应该只是文件仓库，而应该有状态流转：

```text
草稿
→ 已提交
→ 已 Review
→ 可展示
→ 可用于面试
```

每个 Evidence 应能被 Agent 加工成不同表达：

```text
作品集版本
简历 bullet 版本
面试讲述版本
复盘文章版本
```

这会让用户感到自己不是在消耗时间学习，而是在积累可用于转岗、求职、晋升或自我表达的成长资产。

## MVP 优先级

P0 先做完整主循环：

```text
新人快速生成第一步
Today 单一主动作
卡住 / 没时间 / 换任务
Lite Challenge
Evidence 提交
AI Review
自动生成下一步
```

P1 再做阶段能力：

```text
7 天目标
阶段复盘
能力画像更新
```

## 产品评估标准

当前草图的关键评估标准：

| 维度 | 判断问题 |
| --- | --- |
| 新人冷启动 | 用户 3 分钟内是否看到“它懂我”的结果 |
| 日常推进 | 首页是否只有一个清晰主动作 |
| 卡住处理 | 用户是否能不丢脸地降级任务 |
| 学会判定 | 是否用 Lite Challenge 和 Evidence，而不是完成率 |
| 反馈质量 | Review 是否转化成下一步，而不是停留在评价 |
| 作品化 | 用户产出是否能进入作品集、简历、面试表达 |
| 信任感 | 用户是否知道 Agent 为什么推荐这一步 |
