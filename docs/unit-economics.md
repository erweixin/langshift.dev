# 单位经济：每用户成本模型与定价边界

> 这篇回答一个很现实的问题：一个活跃用户每天大概要花多少 LLM 成本？如果订阅卖 $15-20/月，毛利能不能成立？机制层（成本追踪、预算准入、模型路由）见 [llm-provider.md](./llm-provider.md)；本文只放业务参数和粗算方法。

几个词先说清：

- **daily loop**：用户一天里完成的主流程：任务、课程、练习、提交、Review、明日任务。
- **调用面 / surface**：一次 LLM 调用发生在哪个场景，比如课程生成、Review、Coach 对话。
- **band**：内容缓存用的能力大档位，同一档用户更容易复用同一份课程底稿。

## 问题、决策与风险

**问题**：每个 daily loop 都会花 LLM token：课程生成、Review、对话、重写都要钱。如果不知道钱具体花在哪，就没法定价，也没法设计免费层，更不知道内容缓存值不值得做。

**决策**：按“调用面”算账。课程、Review、对话、重写分别指定模型档、token 估算和缓存策略；每次 LLM 调用都带上 `surface` 标签，后面能看清钱花在哪。

**忽略后果**：定价会变成拍脑袋。要么重用户把毛利吃掉了才发现，要么为了省钱全线换小模型，结果 Review 质量塌掉，而 Review 正是用户付费的核心理由。

## 模型分档

| 档 | 用途 | 示例定价（输入/输出，$/MTok）* |
| --- | --- | --- |
| 强 | 课程生成、Review、冷启动诊断 | 5 / 25 |
| 中 | 任务生成、作品化、LessonPlan、断更回归 | 3 / 15 |
| 小 | Drawer 对话、选中重写、画像摘要、校验辅助 | 1 / 5 |

\* 2026-06 主流报价作示例（对应 Opus / Sonnet / Haiku 档）；接入与调价时以 provider 价目为准，参数化在配置里而非写死代码。提示缓存：读 ≈0.1×输入价，写 ≈1.25×（5 分钟 TTL）。

## 每面成本模型

单次调用成本可以粗略写成：

```text
输入 token × 输入单价 × 缓存折扣 + 输出 token × 输出单价
```

更精确一点就是：`tok_in × p_in × (1 - hit × 0.9) + tok_out × p_out`，其中 hit 是前缀缓存命中比例。

每日成本 = 各个调用面相加：`频次 × 单次成本 × 内容缓存未命中率`。

典型活跃日估算（第一条路线、band 已有缓存的稳态）：

| 面 | 档 | 频次/日 | tok_in / tok_out | 关键假设 | 估算成本/日 |
| --- | --- | --- | --- | --- | --- |
| 课程生成 | 强 | 1 | 6k / 5k | **内容缓存命中 70%**（管线基座共享） | ~$0.047 |
| Review | 强 | 1 | 4k / 1.5k | 前缀缓存（系统+规则）命中 | ~$0.052 |
| 任务生成 | 中 | 1 | 3k / 0.5k | | ~$0.017 |
| Drawer 对话 | 小 | 5 轮 | 3k / 0.3k | 前缀（画像+任务）高命中 | ~$0.012 |
| 选中重写 | 小 | 2 | 2k / 0.4k | | ~$0.008 |
| 画像摘要刷新 | 小 | 1 | 2k / 0.3k | | ~$0.004 |
| 作品化 | 中 | 0.2（摊薄） | 3k / 0.8k | | ~$0.004 |
| **合计（典型）** | | | | | **≈ $0.14 / 活跃日** |

情景区间：

| 用户画像 | 假设 | 月成本（20 活跃日） |
| --- | --- | --- |
| 典型 | 上表 | ≈ **$2.9** |
| 重度 | 对话 ×3、重写 ×3、内容缓存未命中（自定义目标） | ≈ **$8–10** |
| 轻度 | 隔天来、少对话 | ≈ **$1** |
| 冷启动一次性 | 诊断 + 路线 + 首课全新生成 | ≈ $0.5 / 人 |

**定价含义**：如果订阅定在 $15-20/月（对标职业辅导，而不是普通笔记工具），典型用户毛利率大约 80%+，重度用户仍能超过 50%。免费层可以按“每周 N 个完整 loop + 对话限额”设计，把边际成本压在 < $1/月/人。**最敏感的两个变量是内容缓存命中率和 Review 输入长度**：前者靠路线标准化，后者靠提交物裁剪，代码太长就放 artifact 引用，不全塞进 prompt。

## 成本护栏

这些护栏和 [llm-provider.md](./llm-provider.md) 的预算准入机制对齐。原则是：先降非核心面，别动 Review 质量。

| 护栏 | 规则 | 触发后 |
| --- | --- | --- |
| 每用户日预算 | 典型成本的 ~5×（如 $0.7/日） | 进入降级阶梯，不是硬拒绝 |
| 降级阶梯 | ① 对话/重写降小模型上下文 ② 课程只出缓存基座（关预重写） ③ Review 转批量（次日晨出结果） | UI 诚实告知，不静默降质 |
| 对话防滥用 | 单日轮次上限 + 连续追问引导回练习（Coach 产品立场本来如此） | |
| 匿名/免费层 | 冷启动诊断限 1 次/账号，重生成收敛 | |

**Review 永不降档**——它是感知价值的核心；宁可延迟（批量半价）不可降质。

## 监控与归因

每次 LLM 调用都要落账，v0 起就做（见 [v0-product-slice.md](./v0-product-slice.md)）：`surface / model / tok_in / tok_out / cache_read / cost / user_id / run_id`。看板先只看四条低基数曲线：

1. cost per DAU（按日）
2. 内容缓存命中率
3. 各面成本占比（饼图，发现异常面）
4. Top 成本用户分布（重用户是分层信号，不是坏事）

## 自部署与托管的成本表达

- **自部署（BYO key）**：成本天然透明——用户自己的 API 账单。产品内仍显示每次调用的 token 消耗（信任 + 教育双重作用）。
- **托管**：订阅价必须覆盖"典型用户成本 × 安全边际 + 记忆/沙箱等增值服务成本"。上表即为定价底线的计算依据，每季随价目与命中率实测重算。

## Do / Don't

| 应该 | 不应该 |
| --- | --- |
| 按面分档、按面归因 | 全线一个模型、成本一锅粥 |
| 价格参数化 + 定期校对价目 | 把单价写死在代码里 |
| 降级阶梯 + 诚实告知 | 静默降质或硬拒绝 |
| Review 保质、其他面找钱 | 为省钱先砍 Review |
| v0 起记录每次调用成本 | 等规模化再补计量 |
