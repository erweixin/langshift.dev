# Stage 3 reference-capacity gate

This gate accepts evidence only from the complete reference production topology. The local foundation Compose file is deliberately ineligible.

The load controller must sustain every vector in `reference-capacity-profile.json` concurrently for at least 1,800 seconds and export a single JSON result. Every measurement must include its Prometheus query, observation count and raw-series SHA-256. The result must also bind the source commit, deployment manifest hash, image digests, hardware/region topology, provider emulator version, runtime image digest, dataset size and wall-clock start/end timestamps.

`scripts/run-stage3-capacity-observer.mjs` is the production observer for that run. It requires a clean checkout at the exact source commit, mutual TLS and bearer authentication for both the load controller and Prometheus, one region with at least two availability zones, and the complete immutable evidence set. It starts the fixed profile through the narrow `/v1/reference-capacity-runs` controller protocol. The controller first reports `warming` while it establishes every public SSE connection and the fixed authenticated API stream; only after the full vector is stable does it atomically report `running` with an immutable `startedAt`. Warmup is capped at 900 seconds and is excluded from evidence. The observer verifies a fresh heartbeat and an unchanged controller timestamp throughout the full measured wall-clock duration, completes the run, then obtains every metric with Prometheus `query_range` over the controller-bound interval. Vectors are reduced to their minimum sustained value; maximum SLOs and zero-tolerance counters use their worst maximum; minimum SLOs use their worst minimum. Exactly one fixed-profile series and at least `116` finite observations at the fixed 15-second interval are required for every query. Every deployment must set `LITES_ENVIRONMENT=stage3-reference-production-v1`; queries bind the exported `deployment_environment_name` resource label to that fixed profile. A per-run identifier is forbidden as a metrics label and remains only in the controller attestation.

The in-repository `reference-capacity-controller` binary is the canonical load controller. Its dataset binds the exact source commit, five equal authenticated tenant buckets, one fixed hot tenant-user, 10,000 SSE connections, pre-seeded Conversation versions and immutable scenario names. It dispatches 510 real `POST /v1/messages` requests per second through the public Gateway with session cookies, CSRF, `If-Match` and idempotency keys; the two-percent fixed margin keeps the measured one-minute rate above the 500 request/second contract across scheduler and scrape boundaries. The hot user receives at least 34 accepted messages per second, proving at least 102 atomic event appends per second from `MessageAppended`, `RunAccepted` and `RunQueued`. The controller fails the run after any 15-second interval below 500 accepted requests/second or above the fixed error ratio. The remaining Provider, Runtime, artifact, token, replay and heartbeat vectors must be produced by the deployed workers and the content-pinned reference scenario/provider-emulator artifacts; the controller cannot publish those product-owned metrics.

Prepare a fresh dataset with `node scripts/seed-stage3-reference-capacity.mjs /absolute/path/seeder-config.json`. The seeder requires five equal tenant buckets totaling exactly 10,000 connections, exactly one hot principal, at least 100 pre-seeded Conversations per principal, a production Gateway mTLS identity, and password files outside Git. It performs real `/v1/auth/login` and `/v1/conversations` calls, requires each returned session to cover warmup plus the full measurement, writes credentials with mode `0600`, and removes the entire newly-created output directory on any partial failure. Copy the completed directory to the read-only PVC mounted at `/run/capacity`; use the printed manifest SHA-256 as `datasetManifestSha256`.

All example queries map to the production metric surface. `lites_capacity_hot_tenant_percent` and `lites_capacity_hot_tenant_user_event_appends_total` are the only controller-owned load-shape metrics; the controller must derive them from its fixed authenticated dataset without tenant IDs or run IDs as labels. Every other query is emitted by the deployed product services. Product services initialize every zero-tolerance invariant series explicitly; the queries deliberately have no `vector(0)` fallback, so absent monitoring data fails the gate instead of being interpreted as zero violations.

Copy `reference-capacity-observer.example.json` outside the repository, replace all example values with the deployed release snapshot and secret-file paths, then run:

```sh
node scripts/run-stage3-capacity-observer.mjs \
  --config /absolute/path/reference-capacity-observer.json \
  --output /secure/evidence/reference-capacity-result.json
npm run gate:stage3:capacity -- /secure/evidence/reference-capacity-result.json
```

The observer aborts the controller run on interruption or validation failure and does not write a partial result. The result file is mode `0600`; it contains no bearer token or private-key material. The example queries are the required metric contract and must be reconciled with the deployed recording rules before the run, not edited after observing results.

Run `npm run gate:stage3:capacity -- /absolute/path/to/raw-capacity-result.json`. The verifier rejects missing vectors, scaled-down profiles, synthetic/local topology, insufficient duration, SLO violations, safety invariant violations, absent raw evidence hashes and source-commit drift. A passing report is written only after all checks succeed.

`npm run gate:stage3:capacity:self-test` exercises the verifier with an in-memory compliant result and one mutation for every threshold. It is a verifier test, not capacity evidence.
